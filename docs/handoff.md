# UNIFIED RESEARCH HANDOFF PACK — PART 1/2

## 1. Research Mission

**Core Problem:**
Build an autonomous LLM-based penetration testing framework targeting DVWA (Damn Vulnerable Web Application), where the primary contribution is a static, pre-validated Attack Knowledge Graph (AKG) that guides LLM method selection and constrains hybrid payload generation within bounded vulnerability domains.

**Exact Objectives (current, post-supervisor revision):**
1. **System Contribution:** Develop an autonomous LLM pentest framework integrating a predefined AKG (NetworkX), LangGraph runtime orchestration, static method agents, validated static payload seeds, and AKG-constrained payload mutation/generation for 3 DVWA vulnerability surfaces at 3 security levels (Low/Medium/High).
2. **Novel Contribution:** Evaluate whether AKG-guided method selection improves over linear, unorchestrated LLM reasoning for bounded web exploitation, using method selection accuracy, adaptation rate, AKG path quality, and attempts-to-success.
3. **Payload Contribution:** Evaluate controlled LLM payload mutation/generation using static validated seeds, method-specific mutation rules, validation rules, expected success signals, and fixed candidate budgets. Payload generation quality is measured separately from method selection and exploitation outcome.
4. **Empirical Contribution:** Compare multiple LLMs (≥1 SOTA commercial + ≥1 OSS) on identical architecture, including model-specific behavior across method families, payload validity, generated payload effectiveness, consistency, guardrail activation, and token cost.

**Scope (finalized):**
- Target: DVWA only (not HackTheBox, not XBOW).
- Vulnerability surfaces: **SQL Injection, Access Control, Brute Force**.
- Per surface: all selected method families tested deeply, not all DVWA modules broadly.
- Security levels: Low / Medium / High per method per surface.
- Multi-LLM comparison: Claude, GPT, open model (Llama/DeepSeek or other open model TBD).
- Payload strategy: validated static payload seeds + constrained LLM mutation/generation, not unrestricted payload generation.
- No fine-tuning. No defense/detection system. No network-layer attacks. No dynamic graph generation.

**Current Stage:**
Architecture designed. Scope narrowed to 3-surface deep-method evaluation. Latest revision adds controlled hybrid payload generation while preserving static AKG and static method-agent architecture.

**Supervisor Recommendation (adopted):**
LLMs should be used for reconnaissance interpretation, AKG-guided attack method selection, and payload generation. Payload generation must be controlled through AKG constraints and validated seed payloads so that probabilistic LLM behavior can be measured without destroying reproducibility.

## 2. Theory Core

### Key Definitions

**AKG (Attack Knowledge Graph) — CURRENT STRUCTURE:**
Static, predefined NetworkX DiGraph. Core node hierarchy:
- Level 1: Surface nodes (`sqli`, `access_control`, `brute_force`)
- Level 2: Method nodes (`sqli_union`, `sqli_error`, `ac_idor`, etc.)
- Level 3 metadata: Payload-generation profile attached to each method node
- Outcome and chain nodes: confirmed vulnerability states and cross-surface chain enablers

The AKG is **not generated by the LLM at runtime**. It is built from domain knowledge, validated manually, and queried during execution for method selection, precondition checking, payload constraints, expected success signals, and chain routing.

**Payload-Aware Method Node:**
A method node contains:
- observable preconditions,
- static seed payload references,
- allowed mutation types,
- forbidden mutation types,
- validation rules,
- expected success signals,
- payload candidate budget,
- provenance requirements,
- scoring hooks.

**Static Method Agent:**
A fixed execution module for a known method family, such as `sqli_union_agent.py`, `ac_idor_agent.py`, or `bf_dictionary_agent.py`. Agents are not dynamically generated. They execute a payload candidate queue built from static seeds and AKG-constrained LLM variants.

**LLM Role (revised):**
The LLM performs:
1. reconnaissance interpretation,
2. method selection over AKG viable nodes,
3. constrained payload mutation/generation based on selected method, seed payloads, security level, observations, and AKG validation rules.

The LLM does **not** create arbitrary agents, arbitrary graphs, or unrestricted payloads.

**Linear Baseline:**
Same LLM, same static agents, same payload seeds, but no AKG-based method filtering, payload constraints, or chain-aware routing. Used to test whether AKG improves reasoning and control.

**Static Payload Baseline:**
AKG-guided method selection using only validated static seed payloads. Used to isolate method selection quality from payload generation quality.

**Hybrid Payload Condition:**
AKG-guided method selection plus static seeds and LLM-generated variants constrained by method node metadata. Used to evaluate model-specific payload behavior.

**Human Baseline:**
Manual operator using validated payload knowledge in DVWA. Treated as upper-bound reference only for feasible objectives. Infeasible cases, such as high-security brute force requiring CAPTCHA solving or external mechanisms, should be marked as scope-boundary or capped rather than treated as ordinary failure.

**Cross-surface chains:**
- `brute_force_confirmed` → `authenticated_session` → `ac_idor`.
- `sqli_confirmed` → `credentials_extracted` → `brute_force_confirmed`.
- `ac_vertical_escalation_confirmed` → `admin_session_obtained` → `sqli_union`.

**AKG Intellectual Lineage:**
1. Sheyner et al. 2002: origin of attack graphs; static + network-level, not web app.
2. PentestGPT 2024: task tree guidance; tree structure, human-assisted, no method-level precondition semantics.
3. VulnBot 2025: Penetration Task Graph generated dynamically at runtime; edge validity not pre-validated.
4. AWE 2026: adaptive payload generation/mutation and structured web exploitation pipeline; lacks static AKG method-precondition structure and does not evaluate method selection quality as primary contribution.
5. This work: static pre-validated payload-aware AKG, domain-specific to DVWA web vulnerabilities, integrated into LangGraph for method selection, constrained payload generation, fallback, chain routing, and separated evaluation.

### Prior Work Analysis

**AWE (Adaptive Agents for Dynamic Web Penetration Testing) — closest payload-generation comparator:**
- Uses adaptive agents and vulnerability-specific pipelines.
- Includes context-aware payload mutation/generation.
- Uses DVWA for model selection but not as the primary deep-method benchmark.
- Uses success-oriented scoring, not separated method selection and payload generation metrics.
- Does not focus on Access Control and Brute Force in DVWA.
- Main relevance: supports the feasibility of LLM-assisted payload mutation, but this thesis adds AKG constraints, static seeds, provenance, and separated evaluation.

**VulnBot:**
- Multi-agent autonomous prototype with runtime-generated PTG and RAG.
- Relevant because it uses graph-like task planning.
- Main distinction: this thesis uses static, manually validated AKG with observable preconditions and payload constraints.

**PentestGPT:**
- LLM-based pentest assistant using task decomposition.
- Relevant for LLM reasoning and context management.
- Main distinction: this thesis is more autonomous, uses static AKG, and evaluates method/payload outcomes in DVWA.

**CurriculumPT:**
- Curriculum-guided autonomous penetration testing.
- Relevant as recent SOTA-style autonomous pentest work.
- Main distinction: curriculum learning is not the same as static domain knowledge graph and payload-aware method selection.

**AutoPenBench:**
- Benchmark for generative agents in vulnerability testing.
- Shows fully autonomous agents remain difficult.
- Supports need for controlled orchestration and reproducible evaluation.

**SecLLMHolmes:**
- Shows LLM security reasoning can be brittle and non-deterministic.
- Supports the need to separate reasoning, payload generation, validation, and execution evidence.

### Key Claims and Caveats

**Core research claim:**
A static, pre-validated, payload-aware AKG can improve controllability, reproducibility, and interpretability of autonomous LLM-based penetration testing by constraining both method selection and payload generation within bounded vulnerability domains.

**Payload-specific claim:**
Validated static payload seeds combined with AKG-constrained LLM mutation/generation provide a controlled way to evaluate model-specific payload capabilities without turning the framework into unrestricted payload synthesis.

**Model comparison claim:**
Different LLMs may show different strengths across method families, such as UNION-based SQLi, time-based blind SQLi, IDOR parameter mutation, or brute-force pacing logic. These differences should be analyzed through payload validity, execution success, consistency, refusal rate, and cost, not only final exploitation score.

**Scope boundaries:**
- AKG validity is bounded to known DVWA vulnerability surfaces and methods.
- The framework does not discover arbitrary unknown vulnerability classes.
- Static AKG cannot model novel runtime-discovered vulnerability combinations unless manually expanded.
- LLM-generated payload candidates must pass validator checks before execution.
- Credential stuffing remains out of scope because DVWA lacks breach-data context.
- High-security brute force may be marked infeasible if CAPTCHA or external solver is required.

**Ruled out:**
- Fine-tuning.
- Dynamic AKG generation by LLM.
- Dynamic agent generation by LLM.
- Jailbreak / adversarial prompt injection.
- Burp Suite integration as core dependency.
- LLM Council / Weighted Majority Voting as core objective.
- Targets outside DVWA.
- Breadth evaluation across all DVWA modules.

### Failure Mode Taxonomy

| Failure Type | Cause | State Update | Scoring Treatment |
|---|---|---|---|
| Content policy refusal | LLM refuses method-selection or payload-generation prompt | Add to `guardrail_activations` or `payload_guardrail_activations` | Do not automatically treat as reasoning failure; report separately |
| Invalid JSON/schema | LLM output fails parser | Add invalid-output event | Retry or fallback; counted in consistency/output-validity metric |
| Invalid payload | Candidate fails validator | Add to `payload_validation_results.rejected` | Payload score 0; not execution failure |
| Precondition not met | Method not viable given observations | AKG returns no viable edge or skips node | Correct skip, not failure |
| Execution failure | Agent executes valid candidate but no expected signal | Add to `failure_agents` and payload attempt log | Exploitation score affected |
| Method selection failure | LLM chooses nonviable or suboptimal method | Add method score | Method selection score affected |
| Chain failure | Exploit succeeds but chain requirement not satisfied | Add chain history | Chain score affected, exploit may still score 3 |

### AttackKnowledgeGraph (core/knowledge_graph.py)

```python
import networkx as nx

class AttackKnowledgeGraph:
    def __init__(self):
        self.G = nx.DiGraph()
        self._build_dvwa_knowledge()

    def _payload_profile(self, seed_refs, allowed, expected, budget=5):
        return {
            "payload_mode": "hybrid",
            "seed_payload_refs": seed_refs,
            "allowed_mutation_types": allowed,
            "forbidden_mutation_types": ["destructive_action", "out_of_scope_target", "wrong_method_family"],
            "validation_rules": ["schema_valid", "method_family_match", "target_param_match", "scope_check"],
            "expected_success_signals": expected,
            "max_generated_candidates": budget,
            "max_total_candidates": budget + len(seed_refs),
            "provenance_required": True,
        }

    def _build_dvwa_knowledge(self):
        self.G.add_node("unauthenticated", type="entry")

        for s in ["sqli", "access_control", "brute_force"]:
            self.G.add_node(s, type="surface")

        self.G.add_node("sqli_union", type="method", surface="sqli",
            preconditions=["union_select_possible"],
            payload_profile=self._payload_profile(
                seed_refs=["sqli_union_low", "sqli_union_medium", "sqli_union_high"],
                allowed=["column_count", "comment_style", "encoding", "quote_strategy"],
                expected=["union_result_visible", "data_extraction_evidence"]
            ))

        self.G.add_node("sqli_error", type="method", surface="sqli",
            preconditions=["error_messages_enabled"],
            payload_profile=self._payload_profile(
                seed_refs=["sqli_error_low", "sqli_error_medium", "sqli_error_high"],
                allowed=["error_function_variant", "encoding", "quote_strategy"],
                expected=["database_error_leakage", "schema_evidence"]
            ))

        self.G.add_node("sqli_boolean_blind", type="method", surface="sqli",
            preconditions=["response_diff_detectable"],
            payload_profile=self._payload_profile(
                seed_refs=["sqli_boolean_low", "sqli_boolean_medium", "sqli_boolean_high"],
                allowed=["predicate_variant", "operator_variant", "encoding"],
                expected=["true_false_response_delta"]
            ))

        self.G.add_node("sqli_time_blind", type="method", surface="sqli",
            preconditions=["response_delay_measurable"],
            payload_profile=self._payload_profile(
                seed_refs=["sqli_time_low", "sqli_time_medium", "sqli_time_high"],
                allowed=["delay_function_variant", "threshold_value", "predicate_variant"],
                expected=["measurable_delay"]
            ))

        self.G.add_node("ac_idor", type="method", surface="access_control",
            preconditions=["object_ids_enumerable"],
            payload_profile=self._payload_profile(
                seed_refs=["ac_idor_low", "ac_idor_medium", "ac_idor_high"],
                allowed=["object_id_sequence", "encoding", "parameter_alias"],
                expected=["unauthorized_object_access"]
            ))

        self.G.add_node("ac_vertical_escalation", type="method", surface="access_control",
            preconditions=["role_based_access_present"],
            payload_profile=self._payload_profile(
                seed_refs=["ac_vertical_low", "ac_vertical_medium", "ac_vertical_high"],
                allowed=["role_parameter_variant", "action_parameter_variant"],
                expected=["privileged_action_accessible"]
            ))

        self.G.add_node("ac_force_browse", type="method", surface="access_control",
            preconditions=["force_browse_endpoints_visible"],
            payload_profile=self._payload_profile(
                seed_refs=["ac_force_browse_low", "ac_force_browse_medium", "ac_force_browse_high"],
                allowed=["endpoint_ordering", "path_normalization"],
                expected=["restricted_endpoint_accessible"]
            ))

        self.G.add_node("bf_dictionary", type="method", surface="brute_force",
            preconditions=["no_rate_limit"],
            payload_profile=self._payload_profile(
                seed_refs=["bf_dictionary_low", "bf_dictionary_medium"],
                allowed=["credential_ordering", "pacing_strategy", "username_priority"],
                expected=["valid_login"]
            ))

        self.G.add_node("bf_spray", type="method", surface="brute_force",
            preconditions=["no_rate_limit"],
            payload_profile=self._payload_profile(
                seed_refs=["bf_spray_low", "bf_spray_medium"],
                allowed=["password_rotation", "account_ordering", "pacing_strategy"],
                expected=["valid_login"]
            ))

        for m in ["sqli_union", "sqli_error", "sqli_boolean_blind", "sqli_time_blind"]:
            self.G.add_edge("sqli", m)
            self.G.add_edge(m, "sqli_confirmed")
        for m in ["ac_idor", "ac_vertical_escalation", "ac_force_browse"]:
            self.G.add_edge("access_control", m)
            self.G.add_edge(m, "access_control_confirmed")
        for m in ["bf_dictionary", "bf_spray"]:
            self.G.add_edge("brute_force", m)
            self.G.add_edge(m, "brute_force_confirmed")

        for o in ["sqli_confirmed", "access_control_confirmed", "brute_force_confirmed",
                  "credentials_extracted", "authenticated_session", "admin_session_obtained"]:
            if o not in self.G:
                self.G.add_node(o, type="outcome")

        self.G.add_edge("sqli_confirmed", "credentials_extracted", is_chain=True)
        self.G.add_edge("credentials_extracted", "brute_force_confirmed", is_chain=True, agent="bf_dictionary_agent")
        self.G.add_edge("brute_force_confirmed", "authenticated_session", is_chain=True)
        self.G.add_edge("authenticated_session", "ac_idor", is_chain=True, agent="ac_idor_agent")
        self.G.add_edge("ac_vertical_escalation_confirmed", "admin_session_obtained", is_chain=True)
        self.G.add_edge("admin_session_obtained", "sqli_union", is_chain=True, agent="sqli_union_agent")

    def get_viable_methods(self, surface: str, observations: dict) -> list[str]:
        methods = []
        for node in self.G.successors(surface):
            if self.G.nodes[node].get("type") == "method":
                preconditions = self.G.nodes[node].get("preconditions", [])
                if all(observations.get(p) for p in preconditions):
                    methods.append(node)
        return methods

    def get_payload_profile(self, method_node: str) -> dict:
        return self.G.nodes[method_node].get("payload_profile", {})

    def get_next_actions(self, state_node: str) -> list[dict]:
        return [{"target": t, **self.G.edges[state_node, t]}
                for t in self.G.successors(state_node)]
```

### Revised Agent Pipeline Pattern

```
Stage 1: PROBE
  → Send observation request
  → Check AKG preconditions
  → Update observations and method score

Stage 2: PAYLOAD CANDIDATE BUILDING
  → Load static seed payload metadata from payload_library
  → If payload_mode = hybrid, ask LLM for AKG-constrained variants
  → Log prompt, response, model, temperature, candidate ID, and provenance

Stage 3: VALIDATION
  → Enforce output schema
  → Check method-family alignment
  → Check target parameter and scope
  → Reject malformed or out-of-method candidates

Stage 4: EXECUTION
  → Static method agent executes candidate queue under fixed budget
  → Verifier checks expected success signals
  → Log evidence

Stage 5: SCORING
  → Score method selection separately
  → Score payload quality separately
  → Score exploitation outcome separately
  → Score chain outcome separately

Stage 6: CHAIN CHECK
  → Query AKG for chain edges from confirmed outcome
  → Dispatch next viable method or finish
```

## 5. Decisions and Rationale

| Decision | Chosen | Rejected | Reason |
|---|---|---|---|
| Orchestration runtime | LangGraph | LangChain alone, PydanticAI alone | Stateful control, conditional routing, checkpointing |
| Graph library | NetworkX | Neo4j, custom dict | In-process, simple, reproducible, research-scale |
| AKG type | Static predefined payload-aware AKG | Dynamic runtime graph | Reproducibility, interpretability, chain correctness |
| Vulnerability scope | 3 surfaces deep-method | All DVWA modules breadth | Depth supports method and payload analysis |
| Agent design | Static method agents | Dynamically generated agents | Reduces implementation variance and preserves auditability |
| Payload strategy | Validated static seeds + AKG-constrained LLM mutation/generation | Unrestricted LLM payload generation or static-only plan | Supports supervisor recommendation while preserving control |
| Evaluation design | Separated method, payload, exploit, chain metrics | Single combined score only | Avoids confounding method selection and payload quality |
| Fine-tuning | Out of scope | Fine-tuned model | Breaks model comparison validity |
| Guardrail metric | Activation rate by prompt type | False positive rate | Activation rate fits offensive sandbox evaluation |
| Evasion | Retry + schema clarification + fallback | Jailbreak / adversarial prompts | Avoids ethically problematic bypass framing |
| Brute force credential stuffing | Out of scope | In scope | No breach-data environment in DVWA |
